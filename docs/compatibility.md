# Совместимость и незакрытые ограничения

| Компонент | Статус |
|---|---|
| Zabbix 8.0 | YAML 8.0 разобран Ruby, проверены ссылки и идентификаторы. Импорт и повторный импорт выполнены на Zabbix 8.0.0; выражения приняты сервером. |
| Script runtime | Код использует ES5 и Zabbix HttpRequest/XML.toJson. Опрашивающие items выполнялись встроенным движком Zabbix 8.0.0 и обрабатывали реальные XML-ответы. Нужна сборка Zabbix с XML-поддержкой. |
| vCenter/vSAN 8.0 U3, OSA/ESA | Проверен один vCenter 8.0.3 с OSA: read-only опрос и session cookie работают. ESA и stretched-кластер не проверены. |
| Официальные VMware-шаблоны | Ключи `vsan.*`, отдельный логический хост; шаблон импортирован на сервер, где уже используется официальный VMware-шаблон; долгосрочная совместная эксплуатация не проверена. Доступность host/datastore повторяется ради связи состояния vSAN и топологии. |
| TLS | `HttpRequest({SSLVerifyPeer:true, SSLVerifyHost:true})` опирается на [код ветки 8.0](https://raw.githubusercontent.com/zabbix/zabbix/release/8.0/src/libs/zbxembed/httprequest.c); поддержку конкретного пакета надо проверить. Доверенный CA — предусловие. Встроенный клиент следует redirects, поэтому нужен прямой доверенный HTTPS endpoint. |

Не реализованы полная инвентаризация всех fault domains и их здоровье, storage policy compliance, суммарные healthy/unhealthy objects при неполных данных API, счётчики компонентов, накопленный трафик/полную скорость копирования/throttling resync и точная детекция застрявшего объекта, резервы operations и host rebuild, effective available capacity, dedup/compression ratio и space efficiency, network I/O/latency/loss/retransmissions. Backend latency и cache hit ratio также не собираются. Для ESA отдельных физических дисков performance API пока не сопоставлен. VM performance зависит от опубликованного `virtual-machine` entity/counters и наличия vSAN datastore в inventory. HCL/firmware compatibility возможны в виде статусов проверок Skyline, но отдельной нормализованной метрики совместимости нет. Отсутствие их в проекте не доказывает, что API не предоставляет эти данные.

Только preferred fault domain с UUID из witness выдаётся в отдельный LLD; список неполон. В ESA структура pool без UUID представлена MoID хоста лишь при единственном pool; при неоднозначности discovery сохраняет предыдущие результаты. Нет полного списка сервисов и состояния stretched cluster. Отдельных items на каждый vSAN object не создаётся. Панели компактные и требуют проверки отображения после импорта; часть запрошенных графиков отсутствует вместе с соответствующими метриками.

Capability discovery частичный: версия API и поддерживаемые performance counters/единицы определяются автоматически, наличие полей и сервисов проверяется по ответу; универсального предварительного discovery всех API-методов нет. Большое число кластеров может превысить timeout или размер ответа; масштабируемость не доказана.

Для возвращённого API состояния `inaccessible` есть отдельный триггер уровня Disaster по каждому источнику. Если такое состояние перестало возвращаться, новое значение не заменяется нулём, а событие закрывается через `{$VSAN.API.NODATA}`; это не подтверждает восстановление. Ошибка или устаревание object-health выдаются отдельно.

На испытанном vCenter `VsanPerfGetSupportedEntityTypes` требовал `System.Read` на корневой inventory-папке. В одной проверенной выборке UI показывал порядок миллисекунд для хостов, тогда как исходные значения API на три порядка выше: преобразование из микросекунд — вывод по наблюдениям, а не подтверждённый поставщиком контракт. Четыре триггера latency отключены до точной сверки одинаковых интервалов. Перепроверьте масштаб и старые точки после обновления шаблона.


Последняя редакция изменила интервалы категорий и добавила ежедневный master для статических параметров дисков из cached health. Эти изменения не проверялись live-import на Zabbix; см. [журнал проверки](validation.md).
